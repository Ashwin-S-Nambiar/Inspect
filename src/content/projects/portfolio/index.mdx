<Project /> is the third version of my portfolio, at ashwin.co.in. It took that address over from v2 on 7 October 2026, and v2 stays up at v2.ashwin.co.in. The home page is one paragraph about me, ending with what I last listened to and watched, and a reel of things I built, each card playing a recording of the real app. Projects and labs have their own pages, and every project gets an essay with figures.

I started it on 25 August 2026, in React, TypeScript and Vite, and kept one rule from the start: no animation library. Every moving thing is a short function I can read, which is what this write-up is about.

## A reel on a curve

The cards ride down the right side of the page on a parabola. Each card's position along the run, from 0 at the top to 1 at the bottom, gives its pose:

```ts
const t = clamp01(p);
const b = bulge(t);

const slope = span > 0 ? (amp * bulgeSlope(t)) / span : 0;
const rot = tilt * Math.atan(slope) * (180 / Math.PI);

return {
  perp: amp * b,
  rot: Math.max(-maxRot, Math.min(maxRot, rot)),
  scale: 1 + lift * b,
};
```

`bulge` is `1 - 4(p - 0.5)²`, so a card sits furthest out at the middle of the screen. It banks to follow the curve's slope, at 45% of the true angle and never more than 9°, and grows by 6% at the top of the bulge. How far the curve bows out isn't fixed either: a 16 step binary search finds the largest bow whose rotated, scaled cards still fit the room beside the paragraph, so a narrow window gets a flatter curve rather than cards off the edge.

The speed is set by the screen, not in pixels: a card takes 18 seconds to cross, however tall the window is. Cards that leave the run pause their video until they come back.

Rest the pointer on the reel and it slows to a stop, so you can read a card. The loop keeps one velocity and nudges it toward a target every frame:

```ts
const dt = Math.min(dtMs, MAX_FRAME_MS);
const k = 1 - Math.exp(-dt / tau);
velocity += (target() - velocity) * k;
```

The target is zero while held and the crossing speed otherwise, and `tau` is 260 ms. Because the step uses the real frame time, it eases the same on a 60 Hz and a 120 Hz screen, and the 50 ms cap stops a background tab from jumping the reel when it comes back.

## Two strips on a phone

A phone has no room beside the paragraph, so below 768 px wide, or under 560 px tall, the curve becomes two straight strips, one above the paragraph and one below, running at 30 px a second in opposite directions. Each strip holds its cards twice and moves by one period, so the loop never shows a seam.

## The last song and the last show

The paragraph ends with the last thing I played on Spotify and the last thing I watched on Simkl. The site is a static Vite build, so two small Vercel functions fetch them. One trades a Spotify refresh token for the current or [last played track](/notes/last-played-not-nothing/). The other passes through [simkl-api](https://github.com/Ashwin-S-Nambiar/simkl-api), a small server of mine that [finds the newest thing](/notes/from-trakt-to-simkl/) in my Simkl history. The browser never calls either service, and the line isn't in the prerendered HTML: it opens once the data lands, so nothing above it jumps.

Neither service sends a title that fits in a sentence. Spotify sends "Kesariya (From "Brahmastra")", "worry - Slowed", or a title with four artists credited inside the brackets. Before a title goes in a chip, it's split into the song, a version, the film it's from and any featured artists:

```ts
for (const group of groups) {
  const feat = /(?:^|,\s*|\s)(?:feat\.?|ft\.?|featuring|with)\s+(.+)$/i.exec(group);
  if (feat) featured.push(...feat[1].split(/\s*(?:,|&| and )\s*/));
  const credits = credited.some((a) => group.toLowerCase().includes(a.toLowerCase()));
  if (feat || credits) continue;
  if (VERSION.test(group)) version = group;
  else context = group.replace(/^from\s+/i, "").replace(/^["'“]|["'”]$/g, "");
}
```

The sentence names one artist or two, and past that "pritam and 2 others", put together with `Intl.ListFormat`. A chip is about 15 characters wide; a longer title fades out at the edge, and on hover it slides by exactly the part that's hidden.

Simkl's history only keeps an anime's original title, so Bleach arrives as "Bleach: Sennen Kessen Hen - Kashin Tan". simkl-api looks up the English one, takes off the "season 17" Simkl adds to it, and splits what's left into show, subtitle and arc. If nothing has played for a week, the music half goes. If one service is down, its half goes, and if both are, the line isn't there at all and the paragraph reads as it did before.

## Columns that know their heights

The projects and labs pages are a masonry of clips and covers. The columns are worked out before any image loads, from aspect ratios kept in the data:

```ts
aspects.forEach((aspect, index) => {
  const height = (aspect > 0 ? 1 / aspect : 1) + gutter;

  let shortest = 0;
  for (let c = 1; c < count; c++) {
    if (heights[c]! < heights[shortest]! - 1e-9) shortest = c;
  }

  out[shortest]!.push(index);
  heights[shortest]! += height;
});
```

Each card goes to the shortest column, counting the gap under it as 7.5% of a column's width, and ties fill from the left. A phone recording is 1:2, so it takes a column's worth of height on its own. The number of columns comes from the width: four from 1240 px, three from 900, two from 500, and one below that, because two columns on a small phone leave a clip too small to read.

## A page before the app

The site is rendered in the browser, so for a moment after a page arrives there's nothing to draw. Instead of a spinner, every route's HTML ships with its own page already inside it. At build time a Vite plugin renders each route from the real components, at several widths, strips the media out and turns the text into shimmer bars. Widths that came out the same are merged, and each version that's left is wrapped so it only shows inside its own width range. When the app starts, it replaces the skeleton with the real page, and since the skeleton came from the same components, nothing moves at any width.

A small inline script drops the skeleton when the URL isn't the one it was built for, so a mistyped link doesn't flash the wrong page's shape on its way to the 404.

Media that arrives within 380 ms, or comes from the cache, or lands off screen, just appears; anything that shows a placeholder for a split second looks like a flicker. Slower media shows a blurred preview of itself, made at build time and stored with the image's real size, and then sharpens in. A phone recording blurs as one picture with its frame, status bar and island, and a failed image keeps its blurred colours with a small image-off mark instead of the browser's broken icon.

That last part had a bug until today. While a phone clip loads, its screen is allowed to spill past its rounded corners so the blur can bleed out softly. That was switched back off only when a clip ended up "ready", and a clip that landed late, while you were watching, ended up "slow" instead. So on a slow connection the screen never got its corners back, and the red of a film poster showed as a thin line down the edge of the phone. The spill now only applies while loading or after an error.

## Rough edges

- **The recordings stay light.** The site follows your system into dark mode, but the clips were recorded in light mode, so they glow on a dark page.
- **Client rendered.** The skeletons, titles and metadata are written at build time, but the page itself needs JavaScript.
- **One reel, one speed.** Holding the reel is the only control; there's no way to scrub it.
- **A minute behind.** The Spotify function caches for 30 seconds and the page asks again every minute, so the line can trail a song change.
- **No card on a phone.** On a touch screen the chips are plain links to Spotify and Simkl; the card only opens with a mouse or the keyboard.
